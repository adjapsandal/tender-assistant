# Tender Assistant

Помощник для участия в госзакупках: ищет тендеры на rostender.info, оценивает,
насколько они подходят компании, и готовит комплект документов для подачи.

Оценка релевантности строится на эмбеддингах. Профиль компании и текст тендера
переводятся в векторы, близость считается косинусной мерой, и тендер попадает
в одну из категорий — от «целевой» до «не подходит». Чем больше выигранных
тендеров загружено в систему, тем точнее профиль: по ним считается центроид —
усреднённый вектор реальных побед, а не описание компании на словах.

Три интерфейса поверх общего слоя логики: Telegram-бот, JSON API на FastAPI
и консольный CLI, с которого начинался проект.

## Что умеет

**Поиск.** Парсинг rostender.info по региону, отрасли и ключевым словам.
Названия вроде «Татарстан» или «Медицина» сайт принимает только как внутренние
идентификаторы, поэтому свободный ввод сопоставляется со справочниками через
языковую модель, а результат кешируется.

**Оценка релевантности.** Тендер и профиль компании сравниваются векторно.
Результат — процент соответствия и категория: целевой, перспективный,
возможный, низкий приоритет или исключён.

**Центроид по выигранным тендерам.** Папки с документами прошлых побед
импортируются, для каждой считается эмбеддинг, из них выводится усреднённый
вектор. Он и становится эталоном, с которым сравниваются новые закупки.

**Анализ вложений.** Прикреплённые к тендеру файлы (PDF, DOCX, HTML)
скачиваются и разбираются на текст, который учитывается при оценке.
Загрузка идёт параллельно, конкурентность ограничена семафором.

**Генерация документов.** Коммерческое предложение, сопроводительное письмо
и ответ на требования собираются моделью на основе реквизитов компании
и условий закупки, выгружаются в DOCX.

**Три интерфейса.** Telegram-бот на aiogram с FSM, REST API с автодокументацией
на `/docs` и CLI для отладки. Слой сервисов, моделей и ML общий — логика
написана один раз.

## Архитектура

```
Telegram (aiogram) ─┐
FastAPI (:8000) ────┼──► services/ ──► PostgreSQL 16 + pgvector
CLI ────────────────┘        │
                             ├──► OpenAI API (эмбеддинги, генерация)
                             └──► rostender.info (поиск, файлы)
```

Модель данных:

```
Company ──┬── WebUser        (вход в API: email + пароль)
          ├── User           (пользователь Telegram)
          ├── SKU            (наборы ключевых слов для поиска)
          ├── Tender ──────── найденные и оценённые закупки
          ├── WonTender ───── выигранные, из них считается центроид
          └── DocumentTemplate
```

Всё принадлежит компании. Компания берётся из `current_user.company_id`,
а не из параметров запроса, поэтому подставить чужой идентификатор нельзя.
Каждый объект перед выдачей сверяется с компанией пользователя, а на чужой
и на несуществующий возвращается одинаковый 404 — чтобы по коду ответа
нельзя было узнать, существует ли чужая запись.

## Быстрый старт

Нужны Python 3.12 и PostgreSQL 16 с расширением pgvector (или Docker).

```bash
git clone https://github.com/adjapsandal/tender-assistant.git
cd tender-assistant
cp .env.example .env        # заполнить ключи и параметры базы
```

**Через Docker — поднимает базу, миграции, API и бота:**

```bash
docker compose up -d
```

**Локально:**

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
alembic upgrade head
python -m scripts.add_demo_company    # компания и её эмбеддинг
uvicorn web_main:app --reload         # API на :8000, документация на /docs
python main.py                        # Telegram-бот
python cli_main.py                    # консольный интерфейс
```

### Переменные окружения

Полный список — в [`.env.example`](.env.example).

| Переменная | Назначение |
|---|---|
| `OPENAI_API_KEY` | Ключ для эмбеддингов и генерации документов |
| `OPENAI_BASE_URL` | Адрес API, если используется прокси |
| `TELEGRAM_BOT_TOKEN` | Токен бота, нужен только для `main.py` |
| `POSTGRES_*` | Параметры подключения к базе |
| `SECRET_KEY` | Подпись JWT, минимум 32 символа. Без него API не стартует |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Время жизни токена |
| `CORS_ORIGINS` | Разрешённые источники через запятую |
| `SIMILARITY_THRESHOLD` | Порог, ниже которого тендер считается нерелевантным |

Секреты в репозиторий не коммитятся: `.env` в `.gitignore`, в `.env.example`
только имена переменных и заглушки.

## pgvector

Оценка релевантности строится на сравнении векторов, поэтому обычного
PostgreSQL недостаточно — нужно расширение
[pgvector](https://github.com/pgvector/pgvector). Оно добавляет тип колонки
`vector` и операторы расстояния, то есть позволяет хранить эмбеддинги рядом
с данными и искать по близости прямо в SQL, без отдельной векторной базы.

### Как используется здесь

Эмбеддинги на 1536 измерений (`text-embedding-3-small`) хранятся в трёх
таблицах:

| Таблица | Что за вектор |
|---|---|
| `companies.embedding` | Профиль компании — эталон, с которым сравниваются закупки. Либо из описания, либо центроид по выигранным тендерам |
| `tenders.embedding` | Текст найденного тендера вместе с содержимым вложений |
| `won_tenders.embedding` | Каждый импортированный выигранный тендер, из них считается центроид |

В модели колонка объявляется типом из `pgvector.sqlalchemy`:

```python
from pgvector.sqlalchemy import Vector

embedding: Mapped[list[float] | None] = mapped_column(Vector(1536), nullable=True)
```

Поиск похожих тендеров идёт средствами базы — сортировкой по косинусному
расстоянию (`database/repositories.py`):

```python
select(Tender)
    .where(Tender.company_id == company_id, Tender.embedding.isnot(None))
    .order_by(Tender.embedding.cosine_distance(embedding))
    .limit(limit)
```

`cosine_distance` разворачивается в оператор `<=>`. Остальные операторы
pgvector: `<->` — евклидово расстояние, `<#>` — отрицательное скалярное
произведение.

Ранжирование по категориям (`ml/ranker.py`) считается в Python: там к
близости добавляются веса по ключевым словам, стоп-словам и совпадению
с SKU, поэтому одной сортировки в SQL не хватает.

### Установка

В Docker ничего делать не нужно: образ `pgvector/pgvector:pg16` уже содержит
расширение, а `init-db.sql` включает его при первом запуске контейнера.

Для своего PostgreSQL — выберите способ под вашу систему. Номер версии
в командах должен совпадать с версией сервера:

```bash
# Debian / Ubuntu
sudo apt install postgresql-16-pgvector

# RHEL / Rocky / Fedora
sudo yum install pgvector_16

# macOS
brew install pgvector
```

Сборка из исходников на Linux и macOS:

```bash
git clone --branch v0.8.6 https://github.com/pgvector/pgvector.git
cd pgvector
make
sudo make install
```

На Windows нужен Visual Studio с поддержкой C++. В консоли
«x64 Native Tools Command Prompt for VS», запущенной от администратора:

```bat
set "PGROOT=C:\Program Files\PostgreSQL\16"
git clone --branch v0.8.6 https://github.com/pgvector/pgvector.git
cd pgvector
nmake /F Makefile.win
nmake /F Makefile.win install
```

Установка кладёт файлы расширения на диск, но в базе его ещё нет. Включить:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

Это делает первая миграция, так что при обычном `alembic upgrade head`
отдельно выполнять команду не нужно. Но `CREATE EXTENSION` требует прав
суперпользователя — pgvector не относится к доверенным расширениям.
Если приложение ходит в базу под обычным пользователем, включите
расширение заранее из-под `postgres`.

Проверить, что всё на месте:

```sql
SELECT extversion FROM pg_extension WHERE extname = 'vector';
```

Пусто — расширение не включено в этой базе. Ошибка `could not open
extension control file` при `CREATE EXTENSION` означает, что оно не
установлено на сервере.

### Индекс

Индекса по векторным колонкам здесь нет: запрос выполняется полным
перебором. На текущих объёмах — тысячи тендеров на компанию — это
незаметно, а точность при переборе стопроцентная. Если записей станут
сотни тысяч, добавьте приблизительный индекс:

```sql
CREATE INDEX ON tenders USING hnsw (embedding vector_cosine_ops);
```

Класс операторов должен соответствовать метрике: для косинусного
расстояния — `vector_cosine_ops`, иначе индекс не будет использован.
HNSW даёт лучшее соотношение скорости и точности и строится сразу;
альтернатива — IVFFlat, он легче по памяти, но требует данных в таблице
на момент создания:

```sql
CREATE INDEX ON tenders USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
```

Оба индекса приблизительные: они ускоряют поиск ценой того, что часть
соседей может потеряться.

## Тесты

```bash
pip install -r requirements-dev.txt
docker compose up -d postgres    # тестам нужен pgvector
pytest -q
ruff check .
```

Тесты идут по HTTP через `httpx.ASGITransport` — без поднятия сервера, но
через все зависимости, включая аутентификацию по куке. База настоящая:
модели используют `Vector(1536)`, на SQLite такая схема не создаётся.
Схема пересоздаётся на каждый тест, обращений к OpenAI и rostender.info нет.

- **`test_auth.py`** — регистрация, вход, отказ анониму, флаг `HttpOnly`
  на куке, выход, отдельная компания на каждого пользователя.
- **`test_authorization.py`** — список маршрутов берётся прямо из приложения,
  и каждый непубличный проверяется на 401 без куки: новый эндпоинт без
  авторизации уронит тест сам. Плюс проверки, что данные одной компании
  не видны другой.
- **`test_import_path.py`** — импорт выигранных тендеров не выходит за пределы
  своего каталога.

CI на GitHub Actions поднимает Postgres с pgvector и гоняет `ruff` и `pytest`
на каждый push и pull request.
